# Payment Reconciliation Engine

**Razorpay AI Buildathon · Track 4 — AI Finance Controller**

> 🔗 **Live demo:** _(deployed Day 5 — link goes here, above the fold)_
> 📊 **Accuracy report:** _(generated by `tools/score` against a held-out answer key)_

Reconciles payments across three deliberately inconsistent financial sources — a payment gateway export, a bank settlement file, and an internal merchant ledger — through a tiered matching engine, classifies whatever it cannot match into an eight-category exception taxonomy, explains each exception in plain English, and logs every decision to a tamper-evident audit trail.

---

## The claim this project is built around

The track's bar is *"throughput plus measured accuracy plus an honest exception list."*

**Measured** is the word that shapes everything here. A match rate the engine prints about itself is not a measurement — if the engine wrongly matches a payment to the wrong bank credit, it counts that as a success and its self-reported rate goes *up*. A number that improves when the system gets things wrong is worse than no number.

So the synthetic data generator writes the **answer key first** and derives the messy files from it. Accuracy is scored offline, by a separate tool, against a truth the engine has never seen and cannot read. And the dataset ships with a **published ceiling**: 7 % of its economic events are designed to be genuinely unresolvable — not merely hard, but impossible for any correct engine and for a competent human looking at the same three files. The maximum honest match rate is therefore ~93 %, and that ceiling is stated up front.

Which means: **anyone reporting 97 % on this dataset is reporting false positives.** The ceiling is its own fraud detector.

**Refusing to guess is a feature.** When two candidates are equally plausible, the engine raises an exception naming both rather than picking the marginal winner. That costs a few points of match rate and buys the thing the track is actually grading.

## Four structural defences against inventing a match

Not policies — properties. Each one makes a class of wrong answer unreachable rather than discouraged:

1. **No-anchor pairs cannot auto-confirm.** A pair sharing no reference number of any kind caps at `0.70` against an auto-confirm threshold of `0.85` — at any amount, on any date, with any name similarity. It falls out of the scoring weights arithmetically. Amount-and-date agreement is a coincidence generator; a reference number is evidence.
2. **Contradicted anchors are disqualifying.** Two strong references that disagree discard the candidate outright rather than scoring it low.
3. **The ambiguity guard.** Top two candidates within 0.05 of each other → the engine refuses to choose and says so.
4. **Direction is a hard gate.** A credit never matches a debit, so a capture can never reconcile against a chargeback.

## Architecture — an engine and an analyst

```
THE ENGINE   (deterministic, reproducible, measured)
3 messy CSVs → INGEST → DEDUPE → TIER 1 exact → TIER 1.5 alias
             → IDENTITY short-circuit → TIER 2 fuzzy → BATCH decomposition
             → CLASSIFY (8 categories) → EXPLAIN → METRICS
                                │
                                ▼  engine output is now final
THE ANALYST  (agentic, bounded, measured against the same key)
             TRIAGE → INVESTIGATE (multi-step tool use) → VALIDATE → PROPOSE
                                │
                                ▼
                        human confirmation
```

A real finance team has a reconciliation system *and* an analyst who works the exception queue it produces. The engine is the first. **The Analyst is the second** — a tool-using agent that investigates exceptions the engine could not resolve, and proposes resolutions with cited reasoning chains a human can check.

The principle that keeps it honest:

> **The agent chooses which questions to ask. Deterministic code computes every answer.**

It never does arithmetic. To learn whether two records match it calls the same scorer the engine used, and gets the same answer the engine would have got. What is agentic is the strategy — which records to pull, which hypothesis to test, when to stop. Its tool registry contains **no mutating tool**, so it cannot write to the database; it proposes, and a human disposes. And a deterministic gate checks every citation against tool calls the agent actually made, so an id it never retrieved is an id it invented — and the verdict is rejected.

It is scored against the same answer key as the engine, which neither can read. **A resolution proposed for a designed-unresolvable exception is a build blocker, not a metric.**

**Stack:** TypeScript everywhere · Node 22 · Express 5 · PostgreSQL 16 (raw SQL, no ORM, no Redis) · Next.js · Anthropic `claude-sonnet-5` for the explain layer only · Vercel + Railway.

**The LLM never decides anything inside the engine.** It receives a decision the deterministic rules have already made and writes a sentence about it. That is what makes a measured accuracy number mean anything — accuracy is a property of the rules, and the rules are deterministic and reproducible from a config snapshot. If the Anthropic API is down, the run still completes with template explanations.

Explanations are cached by **discrepancy signature** — the structural shape of a problem with all specifics stripped — so ~75 exceptions collapse to ~20 distinct shapes and cost stays `O(distinct shapes)` rather than `O(exceptions)`. Re-running the full batch is therefore free, which matters because the track disqualifies cherry-picking.
